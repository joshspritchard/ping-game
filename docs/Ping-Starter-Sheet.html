Your mission

By the end of the week you will have built Ping!, a top-down browser game where you play the new IT technician on a small office campus. You'll publish it on a live link you can show anyone.

How it plays

  1. You start in the IT Office. The ticket printer prints a job sheet: "Sarah's PC can't connect to the wireless network — West Block, Room 3."
  2. You walk your character (WASD or arrow keys) out of the office, across the campus, through the West Block door and into Room 3.
  3. You walk up to Sarah's PC and press E to inspect it. A panel shows its real settings: connection type, Wi-Fi network, IP address, gateway, DNS.
  4. You spot the fault (it's on the guest Wi-Fi, which can't see company servers), fix it, and the device re-tests itself.
  5. Fixed? The ticket closes, and the printer back in your office has the next job waiting.

The campus has a Main Building (IT Office, server room, reception), a West Block and an East Block with offices, a print room and meeting rooms, and a car park. Devices include PCs, laptops, printers, CCTV cameras, Wi-Fi access points and switches.

You start from an empty repository. You will use three tools:

  • GitHub to store your code, track tasks as Issues and publish the game
  • Claude to help you write, explain and debug code
  • VS Code to edit files and run Git

Rules of the week

  1. Explain before you merge. Before you commit code Claude wrote, explain each file out loud to your supervisor. If you can't, ask Claude to explain it until you can.
  2. One Issue, one branch, one pull request. Small steps you can undo.
  3. Coloured squares are fine. Get it working before you make it pretty.
  4. Commit at least once an hour, with a message that says what changed.

What it could look like

These mockups show a finished version: a top-down world drawn with simple shapes, a job bar along the top, and an inspect panel when you look at a device. Use them as a target, not a spec.

The job sheet gives just enough to go on: what's wrong, where, and which device. Finding the cause is the player's job.

The job bar stays on screen while you walk, and the target building is highlighted. Doors switch you from the campus map to that building's rooms.

Each building is its own map. Door signs name the room and the team, so the job sheet's location is all you need to find your way.

Every device is labelled with its owner and how it connects. Walk up to one and a prompt appears; press E to inspect it.

The screen shows what a real technician checks. Internet works but company servers don't, a clue that she's on the guest network. The fix: join CORP-WIFI with the password from the IT Office whiteboard, then re-test.

Setup (first morning, about 1 hour)

The goal of setup is a live web page that says "Ping! coming soon", served from your own repo.

  • Create a free personal account (not a work or school one) at github.com (or sign in)
  • Install Git and VS Code
  • Tell Git who you are, in a terminal:
    • git config --global user.name "Your Name"
    • git config --global user.email "you@example.com"
  • On GitHub, click New repository. Name it ping-game, make it Public, tick Add a README, then Create
  • Click Code → copy the HTTPS URL, then in VS Code: Clone Git Repository and paste it
  • Open Claude (your supervisor will show you which version you're using) and ask it to create index.html with a heading "Ping! coming soon"
  • Commit and push: git add . → git commit -m "Add placeholder page" → git push
  • On GitHub: Settings → Pages → Deploy from a branch → main / (root) → Save
  • After a minute, open https://<your-username>.github.io/ping-game/. That's your live game link.

To run it locally, open index.html in your browser. Once you load level files with fetch, you need a local server instead: in VS Code install the Live Server extension and click Go Live.

Networking cheat sheet

These are the rules the game checks. Each one can be the cause of a ticket.

TermWhat it isExample fault on a ticket
Cable / switch portThe physical link from a wired device to the networkPC unplugged, or plugged into a dead port in the comms cupboard
Wi-Fi network (SSID)The name of a wireless network, e.g. CORP-WIFILaptop joined GUEST-WIFI, which can't see company servers
Wi-Fi passwordThe key needed to join a secured networkPassword changed; device keeps failing to connect
Access pointThe box that broadcasts Wi-Fi in a roomAccess point switched off, so nobody in the room has Wi-Fi
IP addressA device's address, e.g. 192.168.1.10Two devices given the same IP: one drops off
Subnet maskWhich part of the IP is the network, e.g. 255.255.255.0Mistyped mask, so the device thinks the server is "far away"
Default gatewayThe router used to reach other networksGateway blank: local printer works, internet doesn't
DHCPHands out IP settings automaticallyDevice set to a wrong static IP; switch it back to DHCP
DNSTurns names into IPs, e.g. fileserver → 192.168.1.50DNS blank: pinging by IP works, by name fails
PingA test message: "are you there?"The re-test that proves your fix worked

Worked example. With mask 255.255.255.0, the first three numbers are the network. 192.168.1.10 and 192.168.1.20 are on the same network. 192.168.2.5 is not, so traffic to it must go via the gateway.

Project structure

Plain HTML, CSS and JavaScript with a <canvas> for the world: no frameworks, no build step. The world is a grid of 32-pixel tiles. Keep the network rules separate from the drawing code so you can test them on their own.

ping-game/
├── index.html        canvas, job bar, inspect panel, job sheet popup
├── style.css
├── js/
│   ├── main.js       game loop: update, draw, switch maps
│   ├── input.js      keyboard (WASD, arrows, E, Esc)
│   ├── world.js      draws the current map, walls, doors, collisions
│   ├── player.js     position, movement, "what am I next to?"
│   ├── inspect.js    the config screen for a device
│   ├── tickets.js    ticket printer, job sheet, applying faults, closing jobs
│   └── network.js    the rules: testConnection(device, target)
├── data/
│   ├── maps.json     campus, buildings, rooms, doors
│   ├── devices.json  every device and its working settings
│   └── tickets.json  the jobs: which device, what's broken
└── README.md

Maps. Each map (the campus, a building, a room) is a grid of characters. # is wall, . is floor, D is a door, P is the ticket printer. Doors say which map they lead to.

{
  "id": "west-room3",
  "name": "West Block · Room 3 · Finance",
  "grid": [
    "##D#######",
    "#........#",
    "#.d..d..d#",
    "#........#",
    "#.d..d..d#",
    "##########"
  ],
  "doors": [ { "x": 2, "y": 0, "to": "west-corridor", "spawnX": 3, "spawnY": 5 } ]
}

Devices. Each device lives in a room at a tile position and stores its working settings.

{
  "id": "WB-R3-PC1", "type": "pc", "name": "Sarah's PC", "owner": "Sarah, Finance",
  "map": "west-room3", "x": 5, "y": 2,
  "connection": "wifi",
  "wifi": { "on": true, "ssid": "CORP-WIFI", "password": "Ping2026!" },
  "ip": "dhcp", "mask": "255.255.255.0", "gateway": "192.168.1.1", "dns": "192.168.1.5"
}

Tickets. A ticket breaks one setting when it starts, and says what must work again to close it. The same campus gives you many different jobs.

{
  "id": "001",
  "problem": "Sarah's PC can't connect to the wireless network.",
  "location": "West Block, Room 3",
  "device": "WB-R3-PC1",
  "reportedBy": "Sarah, Finance",
  "fault": { "wifi.ssid": "GUEST-WIFI" },
  "fixedWhen": { "canReach": "fileserver" },
  "hint": "Guest Wi-Fi gets the internet but not company servers."
}

The core rule, in plain English (this is what network.js does to test a device):

  1. Is it connected? Wired: cable plugged in and switch port on. Wi-Fi: Wi-Fi on, an access point in the room is on, and the SSID and password are right.
  2. Which network? CORP-WIFI and wired ports are the company network. GUEST-WIFI only reaches the internet.
  3. Does it have a valid IP? DHCP gives one automatically. A static IP must be on the right subnet and not used by another device.
  4. Can it reach the target? Same subnet: yes. Otherwise it needs the right gateway.
  5. By name? Only if DNS is set correctly.

Git workflow (every Issue)

  1. Get the latest code: git checkout main then git pull
  2. Make a branch named after the Issue: git checkout -b 6-can-reach
  3. Build it with Claude. Test it in the browser.
  4. Commit small steps: git add . then git commit -m "Add same-subnet check to canReach"
  5. Push the branch: git push -u origin 6-can-reach
  6. On GitHub, open a pull request. Write what changed and Closes #6
  7. Explain the changes to your supervisor, then click Merge
  8. Check the live link updated (it can take a minute)

Stuck? git status tells you where you are. Ask Claude: "Here's my git status output, what should I do next?"
